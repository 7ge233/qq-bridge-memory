# 事件时效与相对时间归一化设计（v2.3 / Step 6 候选）

> 状态：**设计稿，未实现**
> 适用项目：`qq-bridge-memory`（Python sidecar）+ qq-bridge 接入层
> 目标版本：v2.3（schema v2），不改变现有 v2.2 的存储与召回主流程

## 1. 要解决的问题

当前记忆只存“说话内容 + 说话时间”，不存“这件事本身什么时候发生、什么时候失效”。

例子：

- 10-26 21:00 用户说：“明天我要出去玩”
- 入库：`content = 明天我要出去玩`，`happened_at = 2026-10-26T21:00+08:00`
- 10-29 召回时注入：
  `- [2026-10-26 · 私聊 · 她] 明天我要出去玩`
- 模型看到 10-26，但“明天”没有被换算成 10-27，也没有“已过去”标记；
  30 天半衰期下新鲜度仍约 0.93，排序很靠前，很容易被当成“当前计划”。

同类问题：

- “今晚/后天/下周X/周末/下个月X号”没有绝对日期；
- 用户后来说“没去成/改到周末了”，旧事件不会失效；
- 一次性事件和长期偏好共用 30 天半衰期，事件衰减太慢；
- handoff 的最近原文同样保留“明天”，没有事件日期标注。

**结论：不是“数据库不能全存”，而是“召回时没有判断这件事是否还有效”。**
历史可以全留，问题在注入与否、怎么标注。

## 2. 现状盘点

| 机制 | 现有实现 | 能否解决 |
| --- | --- | --- |
| `happened_at` / `created_at` | `memories` 已分列存储 | 只提供时间，不解释语义 |
| 鲜活度 | `0.5^(天数/30)`，`fact_key` 为 180 天 | 只降权，不做事件有效期 |
| 召回注入 | 行首带日期，块头有“可能过时”声明 | 弱缓解，模型仍可能误读 |
| 时间词加权 | 查询含时间词时分数 ×1.2 | 只影响排序 |
| fact_key 取代 | 同 fact_scope + fact_key 只留最新 | 只适合“身高/偏好”类事实 |
| `conversation_turns` | 90 天流水，handoff 取最近 20 条 | 短期缓解，不解决“明天”语义 |
| 事件状态 | 无 | 缺失 |
| 相对时间归一化 | 无 | 缺失 |

代码位置：

- 建表：`db_init.py` 的 `MEMORY_COLUMNS` 与 `MIGRATIONS`
- 写入：`writer.py` 的 `_build_memory` / `write`
- 召回：`retrieval.py` 的 `freshness_score`、`format_item_line`、`render_block`
- 续接：`handoff.py` 的 `_render` / `_recent_line`
- 时间工具：`timeutil.py`（只做 ISO 解析与格式化）

## 3. 设计原则

1. **全量保留，召回时过滤**：不删历史，只决定是否注入、怎么标注。
2. **宁可少召回，不可把过去当现在**：过期事件默认不进入普通召回。
3. **不猜**：模糊表达（“过两天/改天/下次/有空”）不生成事件时间，保持原行为。
4. **事件与事实分开**：`fact_key` 长期事实继续 180 天；一次性事件走短半衰期和有效期。
5. **向后兼容**：新列可空；旧客户端不传新字段也能工作；关闭开关即回到 v2.2 行为。
6. **可回滚**：新列不破坏旧数据；迁移只加列加索引，不改旧列。

## 4. 数据模型（schema v2）

### 4.1 新增列

```sql
ALTER TABLE memories ADD COLUMN event_at TEXT;
ALTER TABLE memories ADD COLUMN valid_until TEXT;
ALTER TABLE memories ADD COLUMN event_status TEXT;
```

含义：

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `event_at` | TEXT | 事件发生/开始的绝对时间，ISO8601 带 `+08:00`，可空 |
| `valid_until` | TEXT | 事件有效截止时间，ISO8601，可空；为空表示不按事件过期 |
| `event_status` | TEXT | `planned` / `done` / `cancelled`，可空；`expired` 不存储，由召回时计算 |

约定：

- `event_status='planned'`：计划中；过了 `valid_until` 自动视为 `expired`。
- `event_status='done'`：明确已经发生；默认不进入普通召回，只在“过去查询”中出现。
- `event_status='cancelled'`：取消；任何召回都不出现。
- `event_status` 为空：未识别为事件，走旧逻辑（兼容历史数据）。

### 4.2 索引

```sql
CREATE INDEX IF NOT EXISTS ix_mem_event
  ON memories(event_status, valid_until);
```

说明：查询会先按 `account / scope / is_active` 过滤（已有 `ix_mem_scope`），事件过滤是附加条件；该索引用于事件状态与有效期扫描。是否再加 `(account, valid_until)` 复合索引，等真实数据量测试后决定。

### 4.3 归档表同步

`memories_archive` 是 `memories` 的镜像，迁移时为归档表也加同样三列，避免归档/恢复时丢字段。

### 4.4 迁移

- `SCHEMA_VERSION` 从 1 升到 2；
- `MIGRATIONS` 追加版本 2：三条 `ALTER TABLE` + 索引 + 归档表加列；
- `schema_version` 表记录版本 2，`PRAGMA user_version` 同步；
- 迁移必须幂等：重复执行不报错（`ALTER TABLE` 前先检查 `PRAGMA table_info`，已存在则跳过）；
- 旧数据三列为 NULL，不猜测、不回填；
- 回滚：不支持自动降级；从 `backup/` 恢复（6.6 的备份脚本）。

## 5. 相对时间解析（新模块 `temporal.py`）

### 5.1 接口

```python
@dataclass(frozen=True)
class EventTime:
    event_at: str        # ISO8601 +08:00
    valid_until: str     # ISO8601 +08:00
    precision: str       # day | datetime | range
    matched: str         # 命中的原始短语，仅用于日志/调试，不入库

def parse_event_time(text: str, base: datetime) -> EventTime | None: ...
```

- `base` 必须是消息的 `happened_at`，缺失时用 `created_at`，再缺失返回 `None`；
- **不要用“入库时的 now”做基准**，否则补录/重放会算错；
- 解析失败返回 `None`，不抛异常、不影响写入。

### 5.2 支持的模式（V1 规则）

| 类型 | 例子 | 基准日 | `event_at` | `valid_until` |
| --- | --- | --- | --- | --- |
| 今天 | 今天/今晚 | base 当天 | 00:00（今晚 18:00） | 当天 23:59:59 |
| 明天 | 明天/明晚 | base+1 天 | 00:00（明晚 18:00） | 当天 23:59:59 |
| 后天 | 后天 | base+2 天 | 00:00 | 当天 23:59:59 |
| 大后天 | 大后天 | base+3 天 | 00:00 | 当天 23:59:59 |
| 昨天/前天 | 昨天、前天 | base-1/-2 天 | 00:00 | 当天 23:59:59 |
| 周几 | 这周三、下周三、上周五、周三 | 按 ISO 周（周一为 1） | 当天 00:00 | 当天 23:59:59 |
| 周末 | 这周末、下周末、周末 | 周六 | 周六 00:00 | 周日 23:59:59 |
| 下月 | 下个月 3 号、下月 15 日 | 下月 | 当天 00:00 | 当天 23:59:59 |
| 月底/月初 | 月底、下月初 | 对应月 | 当月最后一天/第一天 | 当天 23:59:59 |
| 绝对日期 | 2026-10-27、10 月 27 日、27 号 | 指定日期 | 00:00 | 当天 23:59:59 |
| 具体时间 | 明天下午 3 点、今晚 8 点 | 指定日期 | 15:00 / 20:00 | 当天 23:59:59 |

规则细节：

- “周三”默认指 base 所在周的周三；若已过，仍按本周（不自动顺延），避免猜测；
- “下周X”指 base 所在 ISO 周的下一周；
- “27 号”这类裸日期只在上下文已有时间词或事件语境时启用，避免把“27 号员工”误判成日期；
- **钟点必须有时段前缀或时间后缀才解析**：`明天下午三点`、`今晚八点`、`三点半`、`三点钟`、
  `3:30` 可以；`明天八点`、`明天一点小事`、`早一点/快一点/差一点/两点意见/三点水` 一律只取
  日期（`day` 精度，00:00），不把“一点”当 01:00；
- “月底/月初”用自然月，跨年正确（12 月 → 次年 1 月）；
- 时区固定 `+08:00`（项目约定），跨时区需求另开；
- 一天结束统一为 `23:59:59+08:00`，避免 00:00 边界误判。

### 5.3 明确不解析（返回 None）

- “过两天”“过几天”“改天”“下次”“有空”“回头”“晚点”；
- “每周三”“每个月”“每年”等重复事件；
- 无法判断年份的裸“3 号”且无其他时间词；
- 无时段前缀/时间后缀的裸“X点”（`一点小事`、`早一点`、`两点意见`）→ 只取日期；
- 模糊时段（“下午”“晚上”但没有钟点）→ 可只取日期，精度 `day`；
- 解析不确定时宁可不写，保持旧行为。

### 5.4 事件更新/取消（Phase 2，已实现）

V1 先手动；Phase 2 已加规则（不调模型，保守匹配）：

- 取消词：`不去了 / 不出去了 / 不出去 / 不出门 / 没去成 / 去不了 / 去不成 /
  取消了 / 取消吧 / 不约了 / 计划有变 / 临时有事 / 改天吧 / 又不去了`；
- 改期词：`改到 / 改期 / 改在 / 推迟 / 延后 / 提前到 / 挪到`；
- 问句/提议（`后天怎么样`、`那大后天呢？`）不当作计划，也不更新旧事件；
- assistant 最终拍板（`那就后天 / 选好了就周末 / 确定下周三`）：
  只保留选中日期，取消同 scope、最近 30 分钟内其他 planned 计划；
  选中日期已有计划则保留、不重复建事件；问句不算拍板；
- 在同 scope、`event_status='planned'`、`event_at` 非空的最近 20 条中找**离当前时间最近**的一条；
- 取消：旧事件 `event_status='cancelled'`；
- 改期：重新解析新日期，直接更新旧事件的 `event_at/valid_until`（不新建重复事件）；
  解析不出新日期时只记录、不猜；
- 取消/改期消息本身**不再生成新事件**（避免“明天不去了”变成新的“明天”计划）；
- 找不到候选时也不生成新事件，只记录原话。

## 6. 写入管线改动（`writer.py`）

在现有 `_build_memory` 中：

1. 内容清洗/脱敏后，`category` 已经由规则判定；
2. 仅当 `role='user'` 且 `category='event'` 时调用 `parse_event_time(redacted, base)`；
3. 成功则写入 `event_at`、`valid_until`、`event_status='planned'`；
4. 失败则三列为 NULL，完全保持 v2.2 行为；
5. `fact_key` 记录不参与事件解析（长期事实不设有效期）；
6. assistant 消息不解析事件（避免把“明天见”这类客套存成用户计划）。

需要注意：

- `happened_at` 可能为空：用 `created_at` 兜底；两者都空则不解析；
- 解析只依赖原文，不额外调用模型（V1 约束）；
- 事件写入不改变现有幂等/近似重复/fact 取代逻辑；
- 解析异常只记 `temporal_parse_error` 计数，不影响入库。

## 7. 召回管线改动（`retrieval.py`）

### 7.1 过滤

在现有权限 SQL 之后追加：

```sql
AND (event_status IS NULL OR event_status != 'cancelled')
```

过期判断在 Python 侧做（避免 SQLite 时间字符串比较受格式影响）：

- `valid_until` 非空且 `now > valid_until` → `temporal_state='past'`；
- `event_status='done'` → `past`；
- `event_status='cancelled'` → `cancelled`（已 SQL 过滤）；
- `event_at > now` 或 `valid_until >= now` → `planned`；
- 三列全空 → `none`，走旧逻辑。

默认策略：

- `past` **不进入普通召回**（这是解决“明天变今天”的关键）；
- `planned` 正常参与；
- `cancelled` 永不出现；
- 提供 `include_past` 参数（默认 false），用于“上次/之前”类查询或控制台历史查看。

自动识别“过去查询”只作为可选优化，不默认开启：

- 查询含“上次/之前/昨天/前几天/那次/还记得”时，可自动 `include_past=true`；
- 仍以显式参数优先，避免误判。

### 7.2 打分

- `fact_key` 非空：半衰期 180 天，保持现状；
- `category='event'`：半衰期建议 7 天，从 `event_at` 起算；
- 其他：30 天，保持现状；
- `planned` 且 `event_at` 在未来 3 天内：可加一个小的“临近计划”加成（如 ×1.1），但不要压过相似度；
- `past` 即使被 `include_past` 纳入，也只用原分数排序，不额外加成。

### 7.3 渲染

普通记忆保持：

```text
- [2026-10-26 · 私聊 · 她] 明天我要出去玩
```

有事件时间时改为：

```text
- [2026-10-26 说 · 事件 2026-10-27 · 计划中] 明天我要出去玩
- [2026-10-26 说 · 事件 2026-10-27 · 已过去] 明天我要出去玩
```

规则：

- 仍保留原文，不篡改用户原话；
- 事件日期用 `event_at` 的日期（时间精度到分钟时才显示时间）；
- 状态只显示 `计划中 / 已过去 / 已取消`（取消默认不出现，仅控制台/历史查询可见）；
- 预算仍按 800 字（含新增的状态文字），单条仍 ≤300 字；
- 事件标注会让行更长；超预算时先裁剪内容，尽量保住状态。

### 7.4 响应字段

`/v1/recall` 的 item 追加（不破坏旧字段）：

```json
{
  "event_at": "2026-10-27T00:00:00+08:00",
  "valid_until": "2026-10-27T23:59:59.999+08:00",
  "event_status": "planned",
  "temporal_state": "planned"
}
```

`meta` 增加 `expired_skipped` 计数（只记数量，不记内容）。

## 8. handoff 改动（`handoff.py`）

现状：`conversation_turns` 没有事件字段，最近原文里的“明天”没有标注。

已实现（不新增 turns 列）：

- `recent_turns` 查询补 `message_id`；按 `message_id → memories.event_at` 建轻量映射，
  recent 行追加：`[10-26 21:00] 她：明天我要出去玩（事件 2026-10-27）`；
- `open_loops` 查询排除 `cancelled/done/已过期` 事件，并在未完成事项后标注
  `（事件 YYYY-MM-DD）`；
- 续接包预算仍 1500 字；降级链不变。

召回测试：

- 同一天召回“明天” → `planned`，带事件日期；

- v1 → v2 幂等；
- 旧数据三列 NULL，行为不变；
- 归档表列同步。

### 11.2 验收标准

- “明天我要出去玩”在事件当天召回显示“计划中 10-27”；
- 事件次日普通召回**不再出现**；
- 明确问“上次出去玩是什么时候”时，可通过 `include_past` 找回并标“已过去”；
- 事实/偏好（身高、口味、约定）不被误过期；
- 解析不确定的内容一律保持旧行为，不产生错误日期；
- recall p95 不因新增字段明显上升（解析只在写入侧，召回只多几个字符串比较）；
- 迁移可重复执行，失败可从备份恢复。

  只处理 `user + event + event_at IS NULL`；模糊表达保持 NULL）；GUI 维护页已实现。

### 13.1 回填工具与 GUI 计划

- CLI：`python backfill_temporal.py` 只报告；`--apply` 落库；`--limit` 分批；`--json` 机器可读。
- 核心逻辑：`run_backfill(settings, apply=..., limit=..., backup=...)`，控制台可直接调用。
- GUI 归类：**「维护 → 数据修复」**，不放在 debug；页面要有 dry-run 预览、计数/样例、
  apply 前自动备份、CSRF、审计和二次确认。**已实现** `/console/maintenance`：
  扫描不写库，应用需输入 `BACKFILL` 才执行；页面内嵌只读计划审计。
- 记忆页支持批量操作：一个下拉同时覆盖启用/停用/软删与事件进度，需勾选确认框，写审计。
- 正式库执行策略：先备份 → 副本 dry-run → 人工抽检 → 正式 apply；没有“自动回填”的默认行为。
- 只读审计：`audit_event_plans.py` 扫描最近 N 分钟 planned 事件，报告
  “同 scope 多个日期 / 过期仍 planned”；不写库，人工再决定是否用控制台处理。
  控制台 `/console/maintenance?audit=1` 可直接查看。

## 14. 开放问题

1. 过去事件是“完全不召回”还是“强降权”？本设计默认不召回，避免“把过去当现在”；历史查询走显式 `include_past`。
2. 多日事件（“出去玩一周”）用 `event_at + valid_until` 表示，但解析规则尚未支持“一周/三天”跨度，留待 Phase 3。
3. 取消/改期已按关键词保守实现，仍有误判风险；控制台可手动“取消/完成/恢复”。
4. handoff 已用 `message_id → event_at` 关联，不新增 turns 列。
5. 时区固定 +08:00 是否满足所有部署；跨时区另开需求。
6. 旧数据回填：已提供 `backfill_temporal.py`，默认 dry-run、模糊不猜；是否在正式库 apply
   由管理员在备份后决定，GUI 入口归入「维护 → 数据修复」。

## 15. 结论

- 存储层：**全量保留**，不因为时效删历史；
- 语义层：给“事件”加绝对时间与有效期，给“事实”保持长期；
- 召回层：**过期事件默认不注入**，过去查询显式开启；
- 展示层：注入行同时给“说话日期 + 事件日期 + 状态”，让模型没有机会把“明天”当现在；
- 不改 v2.2 的主链路与降级策略，开关可回滚。
