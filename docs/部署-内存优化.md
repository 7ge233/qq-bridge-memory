# 内存占用与省内存部署

侧车常驻内存：Windows 实测约 **300 MB**，Ubuntu 实测 **344 MB**。钱花在两个地方——
向量模型（90 MB 权重）和 jieba 词典（34.9 万词的前缀树）。

| 阶段 | Windows | Ubuntu 实测 |
| --- | --- | --- |
| 解释器启动 | 13.2 MB | 16.7 MB |
| 加载 jieba 全量词典后 | 118.4 MB | 75.6 MB |
| 再加载向量模型后 | 280.5 MB | 194.9 MB |
| 完整服务（uvicorn 跑起来） | 303.8 MB | **344 MB** |

前三行是三次独立进程的读数，**不能相加**——单独加载模型时没有 jieba 在场，反之亦然。
最后一行才是真实服务，它同时背着词典、模型、FastAPI/uvicorn、SQLite 和运行时缓冲。

量真实服务时注意别取错进程。用 screen 或 nohup 启动时，`pgrep -f` 命中的往往是最外层的包装进程：

```bash
pgrep -af 'uvicorn'          # 看清楚谁是 python，谁只是 screen / bash 壳
pid=$(pgrep -f '\.venv/bin/python .venv/bin/uvicorn' | head -1)
grep -E 'VmRSS|VmHWM|VmSwap' /proc/$pid/status
grep -E '^Pss' /proc/$pid/smaps_rollup
```

实测那台 2 核机器上的分布：VmRSS 344.4 MB、VmHWM 348.7 MB、Pss 341.2 MB 其中匿名内存 296 MB、
文件页 45 MB、swap 0。**匿名内存占绝大多数**，说明它们都在堆上，不是文件映射。
查询不会让内存增长（30 次编码 +0.3 MB）。所以能动的只有这两块，下面按「代价从小到大」排。

下面是同一台 2 核 Ubuntu 上四种配置的实测对比（每项都是重启后的整进程读数）：

| 配置 | RSS | 峰值 | PSS | 匿名内存 | 相对默认 |
| --- | --- | --- | --- | --- | --- |
| 默认（全量词典 + 模型） | 320.7 MB | 348.7 MB | 319.2 MB | 296.0 MB | — |
| 加 glibc / BLAS 限制 | 305.1 MB | 337.0 MB | 301.7 MB | 255.8 MB | −15.6 MB |
| 加限制 + 3 万词词典 | **255.8 MB** | 287.5 MB | 252.1 MB | 206.2 MB | **−64.9 MB（−20%）** |
| 纯关键词模式 + 全量词典 | 164.7 MB | 164.7 MB | 161.6 MB | 142.4 MB | −156.0 MB |

结论很直接：**收益主要来自裁词典（−49 MB），glibc 那几条只有 −16 MB。**
向量模型固定吃约 140 MB（305.1 − 164.7，两侧都用全量词典时才可比）。

## 一、裁 jieba 词典：省约 49 MB，几乎不掉质量

**原理**：jieba 启动时把整个词表装进字典树做前缀匹配，内存大致与词条数成正比。
34.9 万词对应 75 到 100 MB（看平台），取词频最高的 3 万条只要 28 MB。实测整进程 320.7 → 255.8 MB。

**做法**：生成词典，然后用环境变量指过去。

```bash
python scripts/make_dict.py --words 30000 --out dict-30k.txt
export QQ_MEMORY_JIEBA_DICT=./dict-30k.txt
```

生成的词典约 405 KB（3 万条，原词典 34.9 万条），可以放在项目目录里，`.gitignore` 已挡住。

**注意必须按词频排序**。jieba 自带的 `dict.txt` 不是按词频排的（首行词频 3，末行 732），
直接取前 3 万行只会得到一段按字符码点聚集的词表，切词会明显变差。`make_dict.py` 已经做了排序。

**会掉多少**：用 3000 条公开中文聊天语料（LCCC 衍生样本）实测——

| 词典 | 分词与全量一致 | 词集合 Jaccard | FTS recall@6 | MRR |
| --- | --- | --- | --- | --- |
| 全量 | 100% | 1.000 | 99.5% | 0.982 |
| 3 万词 | 63.9% | 0.874 | 99.2% | 0.983 |
| 1 万词 | 51.6% | 0.818 | 98.8% | 0.966 |

同样的测试在 Ubuntu 服务器上跑，结果一致（63.9% / 0.874 / 99.5%→99.2%，MRR 0.983）。
**1 万词并不比 3 万词更省内存**（探针里都是 27.9 MB），质量却继续下降（recall@6 98.8%、MRR 0.966），
所以 3 万词是甜点。

分词序列有三分之一句子不同，但检索结果几乎不变：recall@6 掉 0.3 个百分点。
原因是差异集中在罕用词，而检索命中的是内容词。**线上还是混合检索，向量那一路权重 0.7，
FTS 的这点差别会被进一步稀释。**

## 二、纯关键词模式：省约 140 MB，但丢掉语义召回

**原理**：把模型目录指向空目录并关掉下载，侧车降级成纯 FTS5 检索，不加载 ONNX。实测向量模型吃约 140 MB，
这一模式把整进程从 305 MB 压到 165 MB。

```bash
export QQ_MEMORY_MODEL_DOWNLOAD=0
export QQ_MEMORY_MODEL_DIR=/tmp/empty-models
```

**代价**：问「我喜欢喝什么」而记忆里写的是「乌龙茶」，匹配不到。
适合只做关键词检索、或机器只有 1 GB 的场合。

## 三、Linux 上还能挤一点，但必须先测

**原理**：多线程原生库（onnxruntime、OpenBLAS）的线程池会各自申请内存池，线程回收后
这部分内存不一定还给系统；glibc 默认策略下碎片会累积。

```bash
export MALLOC_ARENA_MAX=2        # 限制 glibc 的 arena 数量
export OMP_NUM_THREADS=1         # onnxruntime 的 OpenMP 线程
export OPENBLAS_NUM_THREADS=1    # numpy 的 BLAS 线程
```

这三条收益取决于机器，**先用下一节的脚本量，别照抄预期值**。实测结果：这三条合计只省 **15.6 MB**（320.7 → 305.1），匿名内存从 296 MB 降到 256 MB，
说明碎片确实被压掉一些，但没有想象中多。**可以留着，但别指望它解决内存问题。**还能考虑用 jemalloc 替换
分配器（`LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2`，装 `libjemalloc2`），
碎片严重时常见 20% 到 40% 的收益，个别发行版会与 onnxruntime 冲突，要跑一天看曲线。

## 四、怎么自己量

```bash
python scripts/mem_probe.py                                   # 量本机 + 跑词典 A/B
python scripts/mem_probe.py --corpus 导出的聊天.txt            # 用别的语料对比
python scripts/mem_probe.py --skip-model                      # 不加载模型，快
```

脚本只读数据库、不联网，输出分阶段内存和词典 A/B 结果，最后给一段 JSON，字段含义写在文件头。

另外两条系统层面的：

```bash
ps -o rss= -p "$(pgrep -f 'uvicorn app:app')"    # 当前常驻
systemd-cgtop -1                                  # 按 cgroup 看整个服务
```

## 五、给 systemd 加护栏

```ini
[Service]
Environment=MALLOC_ARENA_MAX=2
Environment=OMP_NUM_THREADS=1
Environment=QQ_MEMORY_JIEBA_DICT=/opt/qq-bridge-memory/dict-30k.txt
MemoryHigh=420M
MemoryMax=512M
```

`MemoryHigh` 是开始回收内存的线，`MemoryMax` 是 OOM kill 的线，两者都留 20% 余量——
模型加载是突发的，会瞬间冲高。1 GB 的机器还可以开 zram 兜底（`apt install zram-tools`）。

## 六、不要做的事

- **调 `QQ_MEMORY_EMBED_THREADS` 省内存**：实测 threads=2 与 threads=1 差 1 MB 以内，
  只影响编码速度（4.5 ms 变 6.7 ms）
- **把 embedding 放到云端 API**：能省 162 MB，但单次召回从 5 ms 变成 100 到 300 ms，
  会撞上 qq-bridge 侧 300 ms 硬超时；聊天原文还要发给第三方，与 [privacy.md](privacy.md) 冲突
- **开多 worker 分摊**：SQLite 多写者会锁，`--workers 1` 是硬要求

## 切词典档位（2.5）

档位是「按库」记录的：同一个进程只加载一套词典，切换要重算全库分词，所以

* 档位写在 `data/db-profiles.json` 对应条目的 `jieba_dict`（`full` / `3w`）；
* 迁移只写影子列 `tokens_next`，`tokens` 不动，**迁移期间召回完全按原样跑**；
* 完成后要重启侧车：启动时目标词典已加载，才把 `tokens_next` 一次性换成 `tokens`
  并 `rebuild` FTS。这一步是单事务，断电要么全换要么没换，重开再试即可；
* 迁移支持中断续跑：每 200 行提交一次，游标在 `app_meta`，重启后从 `migrate.state`
  接着做。控制台有暂停 / 继续 / 放弃。

实测（Windows，SQLite WAL，同库 12,000 行）：

| 环节 | 耗时 |
| --- | --- |
| 重算 12,000 行 | 1.30 秒（0.11 ms/行） |
| 切换 + FTS rebuild | 0.21 秒 |
| 3 万词词典首次生成 | 0.55 秒（405 KB，之后复用） |

控制台里的预估按 0.6 ms/行算（约 5 倍余量），覆盖小核数、慢磁盘的服务器。

质量代价要说清楚：3 万词档会丢掉一部分低频多字词。332 行真实库实测 95 行分词变化，
「鲸鱼」丢 11 次、「吃白饭」丢 7 次，换来「白饭」「小鲸鱼」等更细的切分。
觉得重要的词可以用黑话词表（L2/L3）补回去，加词后再定向重算这些行。
